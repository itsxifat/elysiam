## What is wrong today (found 2026-11-09)

1. Two senders with two sets of credentials:
   - Website → Tracking (M35b, `storefront.tracking_settings`) sends the website's browser events
     and a `Purchase` when a website or ncom order is **placed** (`purchase_<orderNo>`).
   - Marketing → Meta (M18, `marketing.meta_connections`, `capi_events`) sends a `Purchase` when
     **any** order is **delivered** (event id = order id).
2. The owner fills only Website → Tracking, so chat, phone and desk orders reach no platform. If
   both were filled with one pixel, a website order would count twice (two ids, no dedupe).
3. The brand compose file passes neither `STOREFRONT_TRACKING_*` nor `MARKETING_META_*`, so both
   senders run `fake` on every brand server: nothing has ever left the ERP.
4. Website checkout saves the order with `source: {}` (`storefront/buying.service.ts:431`): no
   UTM, campaign link or click id; the marketing dashboard cannot attribute a website sale.
5. The inbox drops the click-to-message ad referral (`inbox/webhook-payload.ts:221`, `:226`).
6. Nothing tells a platform about a cancel or a return.

## Scope

Built in two parts, like M35:

**M54a: the hub, Meta and GA4, every channel**

1. **One place per brand: Settings → Tracking.** Destinations (Meta, GA4 now; TikTok and Google
   Ads in M54b), the order stage that counts as `Purchase` (default **confirmed**, the owner's
   choice), which stage events go where, the website's event routes and proxy paths (moved from
   Website → Tracking), test mode, consent and retention. Website → Tracking redirects here.
   Marketing → Meta keeps only the spend import.
2. **Existing settings move over without re-entry.** Website → Tracking's pixel, dataset, token,
   GA4 id and secret, routes and paths, and Marketing → Meta's pixel, token, test code and
   "send name and city" when the brand has nothing in Website → Tracking (D-961).
3. **Every channel's orders, by stage.** A new `tracking` module hears `order.created` and
   `order.status_changed` from the outbox and writes one event per order and stage, at most once
   (unique event id), whichever channel the order came from: desk, inbox, phone, website,
   marketplace (ncom). Stages: `placed`, `confirmed`, `delivered` (and partly delivered),
   `returned`, `cancelled`. The chosen stage goes as `Purchase`; the others as custom events
   (`OrderPlaced`, `OrderConfirmed`, `OrderDelivered`, `OrderReturned`, `OrderCancelled`), each
   switchable per destination.
4. **One delivery per destination.** Each event fans out to one delivery row per destination,
   each its own job, retried with backoff on its own, so a GA4 outage never resends to Meta.
5. **The website's signals are kept for later stages.** Checkout records the browser ids (`fbp`,
   `fbc`, `_ga` client and session), the address and browser (IP, user agent) and the page URL
   sealed in `tracking.order_signals`, so a `Purchase` sent at confirmation (hours later) matches
   as well as one sent at checkout. The website's config tells it not to fire a browser
   `Purchase` when the Purchase stage is not `placed`; it fires `OrderPlaced` instead.
6. **Attribution saved on the order.** Checkout takes `utmSource…utmTerm`, the campaign link code
   and the click ids (`fbclid`, `gclid`, `gbraid`, `wbraid`, `ttclid`), all optional. The UTMs and
   the link code go on `sales.orders.source` (the marketing dashboard reads them); the click ids go
   on the sealed signals.
7. **Cancels and returns.** GA4 gets `refund` for a cancelled or returned order whose purchase was
   sent (the difference for a partial delivery); Meta gets the custom stage event (Meta has no
   refund mechanism).
8. **Watching it.** The event log per brand (filters: order, stage, destination, status), each
   destination's last 7 days (sent, failed, skipped, match keys present), Retry on a failed
   delivery, Send test event per destination, and a Tracking card on the order page.
9. **Deploy.** One `TRACKING_PROVIDER` (`fake` | `live`) and `TRACKING_ENABLED` (two-key rule,
   D-257) replace `STOREFRONT_TRACKING_*` and the CAPI half of `MARKETING_META_*`, passed by the
   brand compose file; runbook `docs/runbooks/tracking.md` (test codes first, then live).

**M54b: TikTok, Google Ads and ads in chats**

10. **TikTok Events API** (v1.3 `event/track`): website orders and browser events as `web` with
    the pixel code, `ttclid` and `ttp`; other orders as `offline` with the brand's offline event
    set; `Purchase` (TikTok's name since 2025).
11. **Google Ads through the Data Manager API** (`events:ingest`): the Purchase stage as a click
    conversion (gclid, gbraid or wbraid, plus the hashed phone and email), restated by resending
    the same `transactionId` with the delivered value after a partial delivery. A service account
    key, sealed per brand, added as a user on the brand's Ads account.
12. **Ads in chats.** The inbox reads the click-to-message referral (Messenger and Instagram
    `referral` with `ad_id` and `ads_context_data`; WhatsApp `messages[].referral` with
    `source_id` and `ctwa_clid`), keeps it on the conversation and shows "From ad: …" in the
    thread header. Create order prefills the order's `adId` from it. When the brand gives its
    messaging dataset, a chat order's events go to Meta as `business_messaging` with the
    channel's ids (Messenger `page_id` and `page_scoped_user_id`; Instagram
    `instagram_business_account_id` and `ig_sid`; WhatsApp `whatsapp_business_account_id` and
    `ctwa_clid`), so Meta credits the ad; otherwise they go as `chat`, as today.

**Out of scope (each to a later milestone or a follow-up):**

- Leads to the platforms (Meta `Lead`/`QualifiedLead`, TikTok CRM, Google enhanced conversions

- Value-based and lifetime-value audiences pushed through the APIs (D-259 stays a CSV): **M56**.
- Showroom POS sales: `pos.sales` has no customer, so there is nothing to match (follow-up).
- Snapchat and Pinterest Conversions APIs: the destination interface takes them later (follow-up;

- Several pixels of one platform per brand (D-958).
- The website repository's own change (fire `OrderPlaced`, forward the new optional fields) is

## Data model (schema `tracking`, migrations from 0172)

Every table: `org_id` FK and index, RLS ENABLE + FORCE with the isolation policy, composite
foreign keys `(org_id, x_id)`, minimum grants to `erp_app`.

- `tracking.settings`: one row per brand: `purchase_stage` (`placed|confirmed|delivered`,
  default `confirmed`), `stage_routes` jsonb (stage × destination on/off), `web_routes` jsonb (the
  website's event routes, moved), `proxy` jsonb, `test_mode`, `send_name_and_city`,
  `default_country_code`, `log_retention_days`, `chat_to_ga4` (off), `updated_by`.
- `tracking.destinations`: one per brand and kind (`meta|ga4|tiktok|google_ads`): `enabled`,
  `public_ids` jsonb (pixel or dataset id, messaging dataset id, measurement id, TikTok pixel code
  and offline event set id, Google Ads customer id, login account and conversion action id), the
  secret sealed (`secret_sealed`, `secret_fingerprint`, `key_id`; Meta token, GA4 API secret,
  TikTok access token, Google service-account key), `test_code`, `api_version`, kind-specific
  `options` jsonb (Google: account currency and the BDT rate, D-971), `last_test_at`,
  `last_test_status`. Size-bounded jsonb, shapes checked by the contract on every write.
- `tracking.events`: one per business event: `event_id` (unique per brand among server events),
  `event_name`, `stage` (null for a browser event), `source` (`server|client`), `order_id`
  (composite FK), `value_poisha`, `currency`, masked user, match keys, `custom_data`, the outgoing
  identifiers sealed (`payload_sealed`, cleared once every delivery is final), `expires_at`.
- `tracking.deliveries`: one per event and destination: `status` (`waiting|queued|sent|failed|
skipped`), `attempts`, `response` (the platform's summary, no personal data), `last_error`,
  `sent_at`, `next_attempt_at`. Unique (event, destination). A final row never changes again
  (trigger, as 0086's).
- `tracking.order_signals`: per order: sealed browser ids, click ids, IP, user agent, page URL;
  `expires_at` = 60 days after the order (D-963), purged nightly.
- **M54b:** `inbox.ad_referrals` (inbox module): per conversation: `channel_kind`, `ad_id` or
  `source_id`, `source_type`, `headline`, `source_url` (https only), `ctwa_clid` sealed,
  `received_at`; the latest is the conversation's.
- **Migrated:** `storefront.tracking_settings` and `marketing.meta_connections`' conversion
  columns are copied by the worker's one-time import (secrets re-sealed in app code, D-961); the
  old tables stop being written. `storefront.tracking_events` purges itself out; the old
  `capi_events` stay read-only history. Dropping them is a later migration (follow-up).
- **Order source:** `sourceSchema` gains `campaignLinkCode` (optional, `^[1-9][0-9]{4}$`). No
  column change.

## Domain (`packages/domain/src/tracking/`, pure, tested)

- `stageEvents(purchaseStage, transition)`: which stage events a status change makes;
  `eventIdFor(orderNo, stage)`: `purchase_<orderNo>` for the Purchase stage (the website's id, so
  the browser's and the server's stay one), `<stage>_<orderNo>` otherwise.
- `orderEventValue(facts)`: net item value after discounts, excluding delivery, in poisha (§11's
  delivered-revenue rule; D-960); `refundValue(sent, delivered)`.
- Payload builders, one per platform: `metaServerEvent` (from M35b's `metaEvent`),
  `metaMessagingEvent`, `ga4Payload`/`ga4Refund`, `tiktokEvent`, `googleAdsEvent`; each with its
  normalisation (Meta phone without `+`; TikTok and Google with `+`; Google's gmail dot rule) and
  its time limit (`eventTooOld`: Meta 7 days, GA4 72 hours, TikTok and Google per D-970).
- `actionSourceFor(channel, identifiers)`: website → `website` (needs the page URL), chats →
  `business_messaging` when the identifiers are there, else `chat`; phone → `phone_call`; walk-in
  → `physical_store`; the rest → `other` (D-256).
- `bdtToAccountCurrency(poisha, rate)` through `packages/domain/src/money` (D-971).

**Property and integration tests:**

- Event ids are deterministic and one stage never makes two events, whatever the order of
  repeated outbox deliveries (fast-check over shuffled duplicate transitions).
- Refunds never exceed what was sent; partial delivery + return sums back to the purchase value.
- No payload carries a plaintext phone, email or name (snapshot per platform, as M18's check 3).
- Real Postgres: one Purchase per destination per order across a desk, chat, phone, website and
  ncom order, with `order.status_changed` delivered twice; RLS isolation on every new table; the
  one-time import; a cancel after a sent Purchase making exactly one GA4 refund.

## API

Every route in the route matrix with a fixture; every response through `serializeFor()`.

- `GET/PUT /v1/tracking/settings` (`read`/`update Tracking`: org_admin, marketing).
- `GET /v1/tracking/destinations`, `PUT /v1/tracking/destinations/:kind` (ids and secrets:
  `update TrackingCredentials`, org_admin only, D-558's rule), `POST …/:kind/test`.
- `GET /v1/tracking/events` (log, cursor paged), `GET /v1/tracking/summary` (per destination,
  7 days), `POST /v1/tracking/deliveries/:id/retry` (`update Tracking`).
- `GET /v1/orders/:id/tracking` (`read Tracking`): the order's events and deliveries.
- Website (signed storefront API): `GET storefront/v1/tracking/config` keeps its shape and adds
  `purchaseStage` and the TikTok pixel code; `POST storefront/v1/events` adds optional `ttp`,
  `ttclid`, `gclid`, `gbraid`, `wbraid`; checkout's `tracking` adds the UTMs, `campaignLinkCode`
  and the click ids. All optional: an old website still works.
- Events: subscribers on `order.created` and `order.status_changed` (worker). Queues
  `tracking.deliver` (one job per delivery, `singletonKey` on an `exclusive` queue, D-207),
  `tracking.import_legacy`, `tracking.purge`. No realtime payloads.

## Decisions to add (proposed; written into decisions.md on approval)

- **D-957** RESOLVED by the owner: `Purchase` is sent when an order is **confirmed**, for every
  channel; the other stages go as custom events. Supersedes D-256's delivered Purchase and
  D-552's placed Purchase. A brand may choose `placed` or `delivered` in Settings → Tracking.
- **D-958** One destination per platform per brand.
- **D-959** The hub is its own module and schema (`tracking`); storefront and inbox hand it
  signals through `TRACKING_API`; it reads orders through `ORDERS_API` and the outbox.
- **D-960** An event's value is the net item value after discounts, excluding delivery, in BDT;
  the website's old Purchase used the order total.
- **D-961** The one-time import copies Website → Tracking, then Marketing → Meta's conversion
  settings when the first is empty; secrets are opened with their old code and re-sealed under
  `STOREFRONT_CREDENTIALS_KEY`; it runs once per brand and is idempotent.
- **D-962** Delivery rows per destination, each its own job; a final row is immutable.
- **D-963** Order signals are kept 60 days after the order, so a return can still be matched.
- **D-964** Browser events stay subject to the brand's retention (default 30 days, as D-552).
- **D-965** The website's browser `Purchase` is off unless the Purchase stage is `placed`; it
  fires `OrderPlaced` with the order's id instead.
- **D-966** GA4 gets chat and phone orders only when "chat orders to GA4" is on (off by default):
  Google says Measurement Protocol without a tag gives partial reporting.
- **D-967** A cancel or return after a sent purchase: GA4 `refund` (full, or the difference);
  Meta and TikTok get the custom stage event; Google Ads gets the restated value (M54b).
- **D-968** `TRACKING_PROVIDER` and `TRACKING_ENABLED` replace the two old pairs; `fake` stays the
  default; the brand compose file passes them.
- **D-969** Permissions: new subjects `Tracking` (org_admin and marketing: read, update) and
  `TrackingCredentials` (org_admin: read, update).
- **D-970** (M54b) TikTok: `web` for website orders, `offline` for the rest; `Purchase`; phone
  `+E.164` hashed; no test code is documented, so test mode sends nothing to TikTok and says so.
- **D-971** (M54b) Google Ads: BDT is not a Google Ads currency. A brand sets its account currency
  and a fixed rate; without a rate the conversion goes without a value (counted only).
- **D-972** (M54b) Google Ads via the Data Manager API with a service-account key;
  `UploadClickConversions` is closed to new developer tokens since 2026-06-15. No retraction.
- **D-973** (M54b) A chat order's ad: the conversation's latest referral within 7 days.
- **Unverified integrations:** Meta (server and business messaging), GA4, TikTok and Google Ads
  adapters, each built from the pages read on 2026-11-10 and off until a test with real
  credentials.

## Risks

- **Business messaging needs Meta app permissions** (`page_events`, `whatsapp_business_manage_
events`, `instagram_manage_events`, Access Tier) and a dataset made on the page or WABA. Until
  the brand has them, chat orders go as `chat`. Instagram cannot optimise for purchases.
- **Google Ads currency.** Sending BDT where the account runs in USD would read Tk 1,250 as
  $1,250; D-971 guards it.
- **Meta's 7-day limit** fails the whole request: events are checked one by one before sending.
- **The website repository** must change for `OrderPlaced` and the new fields; until it does,
  the browser `Purchase` is turned off by its route and the server's carries the stored signals.
- **Size.** Two parts, each with its own verify, audit and commit.
